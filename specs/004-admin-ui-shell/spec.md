# Feature Specification: WordPress 風の管理画面 UI（サイト全体のシェル構築）

**Feature Branch**: `004-admin-ui-shell`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "サイトの UI 構築　WordPress 風の管理画面にして"

## Clarifications

### Session 2026-07-17

- Q: Instagram 連携（002）は管理画面のどこに置くか → A: 独立メニュー + 専用ページとしていたが、Instagram 連携機能そのものを削除したため、メニュー・専用ページ・要約ウィジェットはいずれも廃止（2026-09-18）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理画面シェルの中で操作する (Priority: P1)

ログイン済みユーザーがログイン後の画面に入ると、WordPress の管理画面のような構造 —— 左側のサイドバーメニュー、上部の管理バー、右側の広いコンテンツ領域 —— が表示される。既存の機能（ダッシュボード・フォロワーインポート）はサイドバーのメニュー項目としてまとまり、どのページに移動してもこのシェル（枠）は保たれ、コンテンツ領域だけが切り替わる。

**Why this priority**: サイト全体の骨格。これが無いと以降のすべての画面の置き場所（レイアウトの器）が定まらない。既存機能を「管理画面の中の 1 メニュー」として位置づけ直す土台。

**Independent Test**: ログインして各メニュー（ダッシュボード / インポート）を移動し、サイドバー・管理バーが常に表示され、現在地のメニューがハイライトされ、コンテンツだけが入れ替わることを確認できる。

**Acceptance Scenarios**:

1. **Given** ログイン済みユーザーがログイン後の画面を開いている, **When** 画面を見る, **Then** 左サイドバー（メニュー項目一覧）・上部管理バー（サイト名・ユーザー情報・ログアウト）・メインコンテンツ領域が表示される
2. **Given** 管理画面シェルが表示されている, **When** サイドバーのメニュー項目を選ぶ, **Then** コンテンツ領域だけが該当ページに切り替わり、シェルは再読み込みされず、選択中の項目がハイライトされる
3. **Given** どの管理ページにいても, **When** 管理バーのログアウトを実行する, **Then** セッションが破棄されログイン画面に戻る
4. **Given** 未ログインのユーザー, **When** 管理ページの URL に直接アクセスする, **Then** ログイン画面に誘導される（既存のアクセス制御を維持）

---

### User Story 2 - ダッシュボードで全体像を把握する (Priority: P1)

ログイン後の最初の画面（ダッシュボード）で、WordPress のダッシュボードのように複数の「ウィジェットカード」が並び、各機能の要約（最新の取り込み結果など）と、その機能へ移動するリンクが一覧できる。

**Why this priority**: 管理画面の入口として、散らばった機能の現状を 1 画面に集約する。WordPress 風 UI の最も象徴的な体験。

**Independent Test**: ダッシュボードを開き、各機能の要約ウィジェットが並び、それぞれから該当機能ページへ移動できることを確認できる。

**Acceptance Scenarios**:

1. **Given** ログイン済みユーザー, **When** ダッシュボードを開く, **Then** 機能ごとの要約ウィジェット（最新の取り込み概要など）がカード形式で並ぶ
2. **Given** ダッシュボードのウィジェット, **When** ウィジェット内のリンク/ボタンを選ぶ, **Then** 対応する機能ページ（インポート）へ移動する
3. **Given** まだ接続・取り込みがないユーザー, **When** ダッシュボードを開く, **Then** 各ウィジェットは「未設定」状態と最初の一歩への導線を表示する

---

### User Story 3 - 一貫した画面部品でコンテンツが構成される (Priority: P2)

各機能ページのコンテンツが、WordPress 管理画面のような共通部品 —— ページ見出し + 右寄せのアクションボタン、情報を囲うカード（メタボックス）、一覧のテーブル、状態を伝える通知バナー —— で統一して構成される。既存のインポート画面もこの部品セットに載せ替えられる。

**Why this priority**: シェル（US1）とダッシュボード（US2）が成立した上で、各ページの中身の見た目を揃える。体験の一貫性を担保するが、シェルほど土台ではない。

**Independent Test**: インポート一覧ページと詳細ページを開き、共通のページ見出し・カード・テーブル・通知の部品で構成されていることを確認できる。

**Acceptance Scenarios**:

1. **Given** 任意の機能ページ, **When** 画面を見る, **Then** 統一されたページ見出し（タイトル + 主要アクションボタン）が上部に表示される
2. **Given** 一覧を持つページ（インポート履歴など）, **When** 画面を見る, **Then** 共通のテーブル部品（見出し行・行区切り・行内アクション）で表示される
3. **Given** 操作の結果（成功・失敗）が発生した, **When** 結果が返る, **Then** 共通の通知バナー（成功=肯定色・失敗=注意色・支援技術に通知）で表示される

---

### User Story 4 - 画面サイズに応じて操作できる (Priority: P2)

狭い画面（スマートフォン）では、サイドバーが折りたたまれ、ハンバーガー等の操作で開閉できる。広い画面では常時サイドバーが表示され、必要に応じて折りたたんでコンテンツ領域を広げられる。

**Why this priority**: 管理画面はモバイルでも操作されうる。WordPress 管理画面もレスポンシブ対応している。ただし基本骨格（US1）が先。

**Independent Test**: ビューポート幅を変えて、狭い画面でサイドバーが折りたたまれ開閉でき、広い画面で常時表示・折りたたみ切替ができることを確認できる。

**Acceptance Scenarios**:

1. **Given** 狭い画面（モバイル幅）, **When** 管理画面を開く, **Then** サイドバーは折りたたまれ、開閉トグルで表示/非表示を切り替えられる
2. **Given** 広い画面, **When** サイドバーの折りたたみトグルを操作する, **Then** サイドバーがアイコンのみ表示または非表示になり、コンテンツ領域が広がる
3. **Given** サイドバーを開閉した, **When** ページを移動して戻る, **Then** 直前の開閉状態が保持されている

---

### Edge Cases

- メニュー項目が現在のページと一致しない深い階層（機能の詳細ページ、例: インポート結果の個別ページ）にいるとき、親メニューがハイライトされる
- サイドバーを折りたたんだ状態でもキーボードとスクリーンリーダーで全メニューにアクセスできる
- ダッシュボードのウィジェットが参照する機能でエラー・未接続が起きても、ダッシュボード全体は壊れず該当ウィジェットのみ「取得できません/未設定」を表示する
- 画面幅の境界（折りたたみが切り替わる幅）で表示が破綻しない
- ダークモード/ライトモードのどちらでもシェル・部品のコントラストが保たれる（既存のテーマ切替を維持）
- 極端に長いメニュー名・ユーザー名でもレイアウトが崩れない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ログイン後の全ページは、左サイドバーメニュー・上部管理バー・メインコンテンツ領域からなる共通の管理画面シェルの中に表示されなければならない
- **FR-002**: ページ間を移動してもシェル（サイドバー・管理バー）は保持され、コンテンツ領域のみが切り替わらなければならない
- **FR-003**: サイドバーには各機能へのメニュー項目を表示し、現在表示中のページ（詳細ページの場合は親）に対応する項目をハイライトしなければならない
- **FR-004**: 上部管理バーには、サイト名（またはロゴ）・ログイン中ユーザーの識別情報・ログアウト導線・テーマ切替を配置しなければならない
- **FR-005**: ログイン後の最初の画面（ダッシュボード）は、各機能の要約と導線を持つウィジェットカードの一覧で構成されなければならない。ダッシュボードは要約と専用ページへの導線に徹し、機能の実操作（接続/更新/解除・取り込み等）は各機能の専用ページで行う
- **FR-005a**: サイドバーのメニューは「ホーム」（トップ `/`・ダッシュボード）「インポート」の 2 項目とする（Instagram 連携の削除に伴い「Instagram 連携」項目は廃止）
- **FR-006**: ダッシュボードの各ウィジェットは、対象機能が未設定・取得失敗の場合でもダッシュボード全体を壊さず、該当状態と次の一歩の導線を表示しなければならない
- **FR-007**: 各機能ページのコンテンツは、共通の画面部品（ページ見出し + アクション・カード・テーブル・通知バナー）で構成されなければならない
- **FR-008**: 既存機能（ダッシュボード・フォロワーインポート）は、機能を維持したまま管理画面シェルとメニューに統合されなければならない
- **FR-009**: サイドバーは画面幅に応じて挙動を変え、狭い画面では折りたたみ + トグル開閉、広い画面では常時表示 + 折りたたみ切替ができなければならない
- **FR-010**: サイドバーの開閉/折りたたみ状態は、ページ移動をまたいで保持されなければならない
- **FR-011**: 既存の認証・アクセス制御（未ログインは管理画面から締め出す）を維持しなければならない
- **FR-012**: 管理画面シェルと全部品は、キーボードのみで操作でき、現在地・状態変化・通知が支援技術に伝わる（WCAG 2.1 AA 準拠）ようにしなければならない。ライト/ダーク両テーマでコントラスト基準を満たすこと

### Key Entities

- **ナビゲーションメニュー項目**: サイドバーの 1 項目。表示ラベル・アイコン・遷移先・対応する画面範囲（親子関係でハイライト判定に使う）を持つ。本フェーズでは固定の機能一覧（ダッシュボード / インポート）から構成される
- **ダッシュボードウィジェット**: ダッシュボードに並ぶ 1 カード。タイトル・要約内容・状態（設定済み/未設定/取得失敗）・対象機能への導線を持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ログイン後、ユーザーは全機能（インポート）へサイドバーから 1 アクションで到達できる
- **SC-002**: ページ間の移動でシェルが再描画されず、現在地のメニューハイライトが 100% 正しく一致する（詳細ページでの親ハイライト含む）
- **SC-003**: ダッシュボードから各機能の現状（接続の有無・最新取り込みの有無）を、機能ページを開かずに把握できる
- **SC-004**: 管理画面の全ページ・全部品が自動アクセシビリティ検査（WCAG 2.1 AA 相当）でライト/ダーク両テーマとも違反 0 件である
- **SC-005**: モバイル幅とデスクトップ幅の双方で、サイドバー開閉を含む全操作が破綻なく完了できる
- **SC-006**: 既存機能（接続・更新・解除・取り込み・差分・削除）が UI 刷新後もすべて従来どおり動作する（機能のデグレ 0 件）

## Assumptions

- 対象はログイン後の領域（`(authenticated)` 配下）とする。公開ページ（トップ・ログイン・新規登録）は現行のデザインを維持し、本フェーズのシェルは適用しない
- 「WordPress 風」は WordPress 管理画面の**構造・操作パターン**（左サイドバー + 上部バー + メタボックス/リストテーブル/通知）を指し、WordPress のブランド要素（ロゴ・配色・商標）を複製する意図ではない。配色は 既存のテーマトークンを用いる
- 本フェーズは既存機能の**UI 再構成（シェル化 + 共通部品化）**であり、新しいドメイン機能・新規データは追加しない（DB マイグレーションなし）
- メニュー構成は現時点の機能（ダッシュボード / フォロワーインポート）に基づく固定構成とする。ユーザーによるメニュー編集・プラグイン的拡張はスコープ外
- 既存のダーク/ライトテーマ切替・認証・ルーティング保護はそのまま活かす
- 管理者ロールや権限による表示出し分け（WordPress の権限グループ相当）は本フェーズのスコープ外（全ログインユーザーが同一メニュー）
- 対象ユーザーは日本語話者とし、画面文言は日本語で提供する
