# Feature Specification: ユーザー認証（新規登録・ログイン）— Instagram フォロワー管理アプリ初期化

**Feature Branch**: `001-user-auth`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "~/Documents/github/claude-settings からほとんどのファイルをコピーしたものになる。これから Instagram のフォロワー管理アプリを作る。ダイビング関連の情報を消して再実装して。認証認可は Supabase で行う。一旦まっさらにしてログインと新規登録できるところまで"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新規登録してアプリを使い始める (Priority: P1)

Instagram アカウントを運用しているユーザーが、フォロワー管理アプリを使い始めるためにメールアドレスとパスワードでアカウントを作成する。登録が完了すると、ログイン済みの状態でアプリのホーム画面（ダッシュボードの入口となる画面）に到達できる。

**Why this priority**: アカウントがなければ他のすべての機能が使えない。プロダクトの入口であり、最初に成立させるべき最小価値。

**Independent Test**: 未登録のメールアドレスで新規登録フォームを送信し、アカウントが作成されてログイン済み状態のホーム画面に遷移することを単独で確認できる。

**Acceptance Scenarios**:

1. **Given** 未登録のユーザーが新規登録画面を開いている, **When** 有効なメールアドレスと条件を満たすパスワードを入力して送信する, **Then** アカウントが作成され、登録完了後の画面（確認メール案内またはホーム画面）に遷移する
2. **Given** 新規登録画面で入力中, **When** メールアドレスの形式が不正、またはパスワードが最低要件（12 文字以上・英大文字/小文字/数字を含む）を満たさない状態で送信する, **Then** 該当項目に日本語のエラーメッセージが表示され、アカウントは作成されない
3. **Given** すでに登録済みのメールアドレスがある, **When** 同じメールアドレスで新規登録を試みる, **Then** 登録は完了せず、既存アカウントの存在を悪用されない形式のメッセージ（例: 「確認メールを送信しました」等の非開示応答、またはログイン導線の提示）が表示される

---

### User Story 2 - 登録済みユーザーがログインする (Priority: P1)

登録済みのユーザーが、メールアドレスとパスワードでログインし、自分のアカウントのホーム画面に到達する。ログイン状態はブラウザを閉じて再訪しても維持される。

**Why this priority**: 新規登録と対になる認証の基本動線。2 回目以降の利用が成立しないとプロダクトとして機能しない。

**Independent Test**: 事前に作成済みのアカウントでログイン画面から認証し、ホーム画面に遷移すること・再訪時もログイン状態が維持されることを単独で確認できる。

**Acceptance Scenarios**:

1. **Given** 登録済みユーザーがログイン画面を開いている, **When** 正しいメールアドレスとパスワードを入力して送信する, **Then** ログインに成功しホーム画面に遷移する
2. **Given** ログイン画面を開いている, **When** 誤ったパスワードまたは未登録のメールアドレスで送信する, **Then** 「メールアドレスまたはパスワードが正しくありません」等の（どちらが誤りかを特定させない）エラーメッセージが表示される
3. **Given** ログイン済みのユーザー, **When** ブラウザを閉じて再度アプリを開く, **Then** 再ログインなしでログイン状態が維持されている
4. **Given** ログイン済みのユーザー, **When** ログアウト操作を行う, **Then** セッションが破棄され、未ログイン向けの画面（ログイン画面またはトップページ）に遷移する

---

### User Story 3 - 未ログインユーザーのアクセス制御 (Priority: P2)

未ログインのユーザーがログイン必須の画面（ホーム画面など）に URL 直打ちでアクセスすると、ログイン画面に誘導される。逆に、ログイン済みのユーザーがログイン・新規登録画面を開くとホーム画面に誘導される。

**Why this priority**: 認可の基本。これがないと認証の意味がなく、後続のフォロワー管理機能（本人のデータのみ閲覧可能）の前提が崩れる。

**Independent Test**: 未ログイン状態で保護対象 URL に直接アクセスし、ログイン画面へリダイレクトされることを単独で確認できる。

**Acceptance Scenarios**:

1. **Given** 未ログインのユーザー, **When** ログイン必須の画面 URL に直接アクセスする, **Then** ログイン画面にリダイレクトされる
2. **Given** ログイン済みのユーザー, **When** ログイン画面または新規登録画面の URL にアクセスする, **Then** ホーム画面にリダイレクトされる

---

### User Story 4 - 旧アプリ（ダイビングログ）の痕跡が存在しない (Priority: P2)

このリポジトリは既存のダイビングログアプリからコピーされているため、ユーザーがアプリのどの画面・導線をたどっても、ダイビング関連の機能・文言・データ構造に到達しない。アプリは Instagram フォロワー管理アプリとしての名称・説明で一貫している。

**Why this priority**: 「一旦まっさらにする」という要求の中核。旧機能が残っていると新規開発の土台が汚染され、ユーザーにも混乱を与える。

**Independent Test**: 全画面・全ルートを巡回し、ダイビング関連の画面・文言が表示されないこと、旧機能の URL が到達不能（404 等）であることを確認できる。

**Acceptance Scenarios**:

1. **Given** アプリを利用する任意のユーザー, **When** トップページ・認証画面・ホーム画面を閲覧する, **Then** ダイビング関連の文言・機能は一切表示されず、Instagram フォロワー管理アプリとしての名称・説明が表示される
2. **Given** 旧アプリの機能 URL（ダイビングログ・器材・ライセンス等）を知っているユーザー, **When** その URL に直接アクセスする, **Then** ページは存在しない（Not Found）か、新アプリの適切な画面に誘導される
3. **Given** 開発者がデータ基盤を確認する, **When** データベースのスキーマ定義を確認する, **Then** ダイビング関連のテーブル・関数は存在せず、認証に必要な最小限の構造のみが定義されている

---

### Edge Cases

- 確認メールのリンクを踏む前に（メール未確認状態で）ログインを試みた場合、未確認である旨と再送手段が案内される
- 新規登録の送信を連打（二重送信）しても、アカウントは 1 つしか作成されない
- セッションの有効期限が切れた状態で保護画面を操作した場合、ログイン画面に誘導され、再ログイン後に利用を継続できる
- パスワード入力欄はマスク表示され、表示/非表示の切り替えができる
- ネットワークエラーや認証基盤側の障害時には、ユーザーに日本語の汎用エラーメッセージが表示され、入力内容は失われない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはメールアドレスとパスワードによる新規アカウント登録を提供しなければならない
- **FR-002**: システムは登録時にメールアドレスの形式検証と、パスワードの最低要件（12 文字以上・英大文字/小文字/数字を含む・72 文字以下）の検証を行い、不正な入力には項目ごとの日本語エラーメッセージを表示しなければならない
- **FR-003**: システムは新規登録時に確認メールを送信し、メールアドレスの実在確認を行わなければならない
- **FR-004**: システムはメールアドレスとパスワードによるログインを提供しなければならない
- **FR-005**: ログイン失敗時のエラーメッセージは、メールアドレスとパスワードのどちらが誤っているかを特定できない表現にしなければならない
- **FR-006**: システムはログイン状態をブラウザ再訪後も維持し、明示的なログアウト操作でセッションを破棄できなければならない
- **FR-007**: システムはログイン必須画面への未ログインアクセスをログイン画面へリダイレクトし、ログイン済みユーザーによる認証画面（ログイン・新規登録）へのアクセスをホーム画面へリダイレクトしなければならない
- **FR-008**: ログイン後のホーム画面には、ログイン中のユーザーであることが分かる表示（例: 登録メールアドレス）とログアウト導線を提供しなければならない
- **FR-009**: アプリの全画面から旧アプリ（ダイビングログ）の機能・文言・導線を除去し、Instagram フォロワー管理アプリとしての名称・説明に統一しなければならない
- **FR-010**: データ基盤から旧アプリのテーブル・関数・ポリシー定義を除去し、認証済みユーザーの基本情報を保持する最小限の構造のみを定義しなければならない
- **FR-011**: ユーザーの基本情報は本人のみが参照・更新できるようアクセス制御されなければならない
- **FR-012**: 認証フォーム（新規登録・ログイン）はキーボードのみで操作完結でき、支援技術でエラーが読み上げられる（WCAG 2.1 AA 準拠）ようにしなければならない

### Key Entities

- **ユーザーアカウント**: 認証の主体。メールアドレス・パスワード（秘匿保管）・メール確認状態・登録日時を持つ
- **ユーザープロフィール**: アカウントに 1:1 で紐づく基本情報。将来のフォロワー管理機能（Instagram アカウント連携・フォロワーデータ）の親となる最小限の器で、本フェーズでは識別子・作成日時等の最小構成とする

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新規ユーザーが登録開始からログイン済みホーム画面到達まで 3 分以内（確認メール操作含む）に完了できる
- **SC-002**: 登録済みユーザーがログイン開始からホーム画面到達まで 30 秒以内に完了できる
- **SC-003**: 全画面を巡回してもダイビング関連の文言・機能・到達可能な旧 URL が 0 件である
- **SC-004**: 未ログイン状態で保護対象 URL にアクセスした場合、100% ログイン画面に誘導される（保護漏れ 0 件）
- **SC-005**: 認証フォームが自動アクセシビリティ検査（WCAG 2.1 AA 相当）で違反 0 件である

## Assumptions

- 認証方式は本フェーズではメールアドレス + パスワードのみとする。Instagram（Meta）や Google 等のソーシャルログインは将来フェーズで検討する
- パスワードリセット（忘れた場合の再設定）は「ログインと新規登録まで」という指示に基づき本フェーズのスコープ外とする
- Instagram フォロワーデータの取得・表示・分析などフォロワー管理の本体機能はすべて後続フェーズとする。本フェーズのホーム画面は「ログインできたことが分かる」最小限のプレースホルダーで良い
- リポジトリは初期コミットのみの新規プロジェクトであるため、旧アプリ（ダイビングログ）のコード・仕様書（specs/ 配下の旧番号）・データベースマイグレーションは履歴保全せず削除して再スタートして良い
- 認証・認可の基盤には Supabase（Auth + RLS）を利用する（ユーザー指定）。メール確認や本人のみアクセス可能とする制御はその標準機能の範囲で実現する
- 対象ユーザーは日本語話者とし、画面文言・エラーメッセージは日本語で提供する
- 管理者向け機能（admin）は本フェーズのスコープ外とする
